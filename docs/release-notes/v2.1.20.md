# Synapse v2.1.20: "where the metadata lives"

Patch release completing OAuth discovery for the remote MCP surface, after 2.1.18 and
2.1.19 fixed the scheme. No schema migrations, no new configuration keys. The only new
route is a second path for an existing document.

## Fixed

Behind the Cloudflare Tunnel an MCP client (claude.ai custom connector, `mcp-remote`,
Claude Code) that hit `/mcp/server` without a token could not find the authorization server:

1. **The 401 did not say where the metadata is.** It answered `WWW-Authenticate: Bearer`
   with no `resource_metadata`, so clients had to guess well-known URLs (RFC 9728 §5.1).
   It now answers
   `Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp/server"`,
   with the origin built by the same proxy-aware helper as the OAuth issuer
   (`runtime_state.public_origin`).
2. **The path-suffixed metadata URL did not exist.** RFC 9728 §3.1 inserts the resource
   path after the well-known prefix, and that is the URL MCP clients probe first. The
   backend now serves `/.well-known/oauth-protected-resource/mcp/server` with the same
   document as the root path, behind the same `remote_mcp_enabled` floor.
3. **The frontend nginx answered every other well-known URL with the SPA.** A `200`
   `text/html` for `/.well-known/oauth-protected-resource/mcp/server` or
   `/.well-known/openid-configuration` is a broken document to a client, not a reason to
   fall back. The OAuth location now accepts an optional path suffix and every other
   `/.well-known/` URL is a `404`.

Verified with backend tests (`tests/test_mcp_oauth.py`) and with `nginx:alpine` running the
shipped template.
